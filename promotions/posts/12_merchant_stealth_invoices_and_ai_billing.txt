--------------------------------------------------------------------------------
1.1 ARCHITECTURAL MECHANICS
--------------------------------------------------------------------------------

1. STEALTH DESTINATION DERIVATION:
   Instead of publishing a static payout address, the merchant uses the Dual-Key Stealth Address Protocol (DKSAP). For each order, an ephemeral secret $r$ is generated against the merchant's scan key $A$ and spend key $B$:
   $$P = \mathcal{H}_s(r \cdot A) \cdot G + B$$
   To outside chain observers, $P$ is an anonymous, unlinked address that appears once and is never reused.

2. REGISTERING THE INVOICE:
   The merchant calls `createInvoice()` on-chain:
   ```solidity
   function createInvoice(
       bytes32 invoiceId,
       bytes32 stealthRecipient,
       address claimAddr,
       address token,
       uint256 amount,
       bytes calldata encryptedMemo
   ) external;
   ```
   • `invoiceId`: A unique cryptographic hash committing to the order parameters.
   • `claimAddr`: The one-time stealth address authorized to receive payment.
   • `encryptedMemo`: Arbitrary invoice metadata (order SKU, shipping address, service agreement, or tax reference) encrypted under the counterparty's view key using authenticated ECIES / ChaCha20-Poly1305.

3. ATOMIC SETTLEMENT & PAYMENT NULLIFIERS:
   The customer pays the invoice by invoking `settleInvoice()`:
   ```solidity
   function settleInvoice(
       bytes32 invoiceId,
       bytes32 paymentNullifier
   ) external nonReentrant;
   ```
   • The contract verifies `inv.amount > 0` and `!inv.settled`.
   • The contract checks that `paymentNullifier` has never been used (`!usedPaymentNullifiers[paymentNullifier]`).
   • Tokens are transferred directly from `msg.sender` to the merchant's `claimAddr`.
   • Marks `inv.settled = true` and `usedPaymentNullifiers[paymentNullifier] = true`.
   • Replay attacks and double-payment disputes are mathematically eliminated.

4. ENCRYPTED ON-CHAIN MESSAGING:
   Merchants and buyers can exchange encrypted messages (shipping tracking numbers, fulfillment receipts, refund requests) directly on-chain:
   ```solidity
   function sendEncryptedMessage(
       bytes32 recipientPubkey,
       bytes32 ephemeralPubkey,
       bytes calldata ciphertext
   ) external;
   ```
   Only the holder of the corresponding view key can decrypt the message. Zero data leaks to third parties.

--------------------------------------------------------------------------------
2.1 ARCHITECTURAL MECHANICS
--------------------------------------------------------------------------------

1. CREDIT DEPOSIT UNDER BLINDED COMMITMENT:
   The AI agent (or its managing DAO) pre-funds compute credits into `UsageVault.sol`:
   ```solidity
   function depositCredits(bytes32 commitment, uint256 amount) external nonReentrant;
   ```
   The commitment blinds a 32-byte secret preimage:
   $$\text{Commitment} = \text{Keccak256}(\text{secretPreimage})$$
   At deposit time, no compute provider is specified. The blockchain only records that tokens were escrowed under an anonymous commitment hash.

2. OFF-CHAIN MICRO-TICKET STREAMING:
   When the AI agent initiates an inference request (e.g. 100,000 prompt tokens, image generation, or web-scraping batch), it passes a ticket off-chain:
   $$\text{Ticket} = \big( \text{secretPreimage},\, \text{ticketNullifier},\, \text{amount} \big)$$
   The GPU provider computes $\text{Keccak256}(\text{secretPreimage})$ in memory (< 1 microsecond). If it matches an active commitment on-chain, the compute service immediately processes the inference workload without waiting for block confirmations.

3. ZERO-LINKAGE REDEMPTION & REPLAY PROTECTION:
   The compute provider settles tickets on-chain at their convenience (e.g. hourly or daily):
   ```solidity
   function redeemUsageTicket(
       bytes32 commitment,
       bytes32 ticketNullifier,
       uint256 amount,
       bytes32 secretPreimage
   ) external nonReentrant;
   ```
   The contract performs three strict cryptographic validations:
   • Verifies `keccak256(abi.encodePacked(secretPreimage)) == commitment`.
   • Verifies `!redeemedTickets[ticketNullifier]`.
   • Verifies `creditCommitments[commitment] >= amount`.
   
   Upon verification:
   • `redeemedTickets[ticketNullifier] = true`.
   • `creditCommitments[commitment] -= amount`.
   • `providerEarnings[msg.sender] += amount`.

4. AGGREGATED EARNINGS WITHDRAWAL:
   Providers call `claimEarnings()` to withdraw accumulated revenue in bulk, minimizing on-chain gas overhead:
   ```solidity
   function claimEarnings() external nonReentrant returns (uint256 amount);
   ```

5. CRYPTOGRAPHIC GUARANTEE:
   Because the ticket preimage is transmitted off-chain and the deposit was blinded, chain-surveillance heuristics can never determine which AI agent consumed compute from which provider.
